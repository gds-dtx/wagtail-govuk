# Reporting a vulnerability

**Please do not report security vulnerabilities through a public GitHub issue,
pull request or discussion.** An issue is visible to everyone the moment it is
filed, including to whoever would exploit it.

## How to report

Report it through the government's
[Vulnerability Reporting Service](https://vulnerability-reporting.service.security.gov.uk/).
That is the route this service publishes: every instance built from this
codebase redirects `/.well-known/security.txt` there
(`SECURITYTXT_LOCATION`, `govuk/settings/base.py`). Using it means the report
reaches the people who can act on it whether or not the affected site is one
this team runs.

If the vulnerability is in the code rather than in a running site, and it is
already public — a dependency advisory, say — a GitHub issue is fine.

Please include enough to reproduce it: the URL or the file and line, what you
did, what happened, and what you expected. If you have a proof of concept, say
so and we will arrange somewhere to send it.

## What to expect

The Vulnerability Reporting Service acknowledges reports and routes them to the
service owner. We will confirm whether we can reproduce the issue, tell you what
we intend to do, and let you know when a fix ships.

Please give us a reasonable opportunity to fix an issue before disclosing it
publicly. We will not take legal action against anyone who reports in good
faith, follows the Vulnerability Reporting Service's terms, and does not access,
modify or delete data belonging to other people.

## Scope

This repository is the application. A running instance also involves
infrastructure defined in
[`wagtail-iac`](https://github.com/gds-dtx/wagtail-iac) and per-instance
configuration in `wagtail-instances`. A report about a running site is in scope
wherever the cause turns out to live — you should not have to work out which
repository is at fault before reporting.

Out of scope: findings that require an already-compromised administrator
account, reports generated by a scanner with no evidence of exploitability, and
missing hardening headers on endpoints that serve no content.

## What we do already

Recorded in [docs/security.md](docs/security.md): the response headers and their
settings, the authorisation model, the dependency policy, and the results of the
history secret sweep. That document also states plainly what has **not** been
done — most importantly that this build has never had an independent
penetration test.
